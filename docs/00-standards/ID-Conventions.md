# ID 与可追溯性约定

稳定 ID 是 AI 就绪文档的支柱：它们让代理、测试套件和提交可以无歧义地引用*同一项*需求。本标准定义 ID 方案和可追溯性模型。

---

## 1. ID 方案

| 实体 | 模式 | 示例 | 规则 |
|------|------|------|------|
| 文档 | `<TYPE>-NNN` | `STD-001`、`PRD-001` | 仓库内唯一，永不复用 |
| Epic | `EPIC-NN` | `EPIC-02` | 两位数字，顺序递增 |
| 功能需求 | `FR-<DOMAIN>-NNN` | `FR-OCR-004` | 领域代码见第 2 节，3 位数字 |
| 非功能需求 | `NFR-<CAT>-NNN` | `NFR-PERF-001` | 分类代码见第 3 节 |
| 验收标准 | `AC-<REQID>-NN` | `AC-FR-OCR-004-01` | 将 AC 关联至其需求 |
| 数据实体 | `DM-<Entity>` | `DM-Document` | PascalCase 实体名 |
| 数据字段 | `DM-<Entity>.<field>` | `DM-Document.po_number` | snake_case 字段 |
| API 端点 | `API-N` | `API-3` | 在 API 规范中顺序递增 |
| 架构决策 | `ADR-NNN` | `ADR-001` | 顺序递增且不可变 |
| 测试用例 | `TC-<REQID>-NN` | `TC-FR-OCR-004-01` | 与 AC 编号对应 |

### 不可变规则
- ID 一经发布，**永不**变更或复用。
- 删除需求时：设置 `status: deprecated`，保留 ID 和墓碑说明。
- 拆分需求时：废弃父需求，创建新的子需求 ID。

## 5. 可追溯性模型

每项需求向**上**链接其来源，并向**下**链接其验证：

```
PRD §4.2  ──source──▶  FR-OCR-004  ──verified_by──▶  AC-FR-OCR-004-01
                          │                                   │
                          │ depends_on                        │ implemented_as
                          ▼                                   ▼
                     FR-UPLOAD-002                        TC-FR-OCR-004-01 (test)
                          │
                          └── realized_in ──▶ DM-Document, API-2 (design)
```

### 必需的可追溯性字段（位于 frontmatter 或需求块中）

| 字段 | 方向 | 用途 |
|------|------|------|
| `source` | 上游 | 满足的 PRD 章节 / 利益相关者需求 |
| `depends_on` | 横向 | 必须先存在的需求 |
| `related` | 横向 | 非阻塞关系 |
| `verified_by` | 下游 | 验收标准 ID |
| `realized_in` | 下游 | 数据模型 / API / 组件 ID |

## 6. 可追溯性矩阵（维护于 `Requirements-Index.md`）

每当新增或变更需求时，必须保持矩阵同步。列如下：

| ID | 标题 | 优先级 | 来源（PRD） | 依赖项 | 验证方式 | 设计引用 | 状态 |
|----|------|--------|-------------|--------|----------|----------|------|

**覆盖率检查（在评审时执行）：**
- 每个 PRD “【必需】”章节均映射到至少 1 个 `FR-*`/`NFR-*`。
- 每个 `FR-*` 至少有 1 个 `AC-*`。
- 每个 `AC-*` 至少有 1 个 `TC-*`（测试），或明确标为人工测试。
- 不存在孤立设计元素（每个 `DM-*`/`API-*` 都可追溯至一项需求）。
